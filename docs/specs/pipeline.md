# Spec: end-to-end validation pipeline (v1)

Status: approved for implementation (2026-11-14); all protocol settings are decided. The owner of the repository and of this spec is the benchmark owner;
the implementer maintains this text and the owner reviews spec edits (2026-11-15).
Spec edits are committed separately before their implementation.

- Every protocol setting lives in `protocols/forecast_v1.json`, so changing one never needs a code
  change.
- Anything not covered here is a question for the planner, not a decision for the implementer.

## 0. Goal and principles

Group members train different GRMHD forecasting models (TRON, ViT, UNO variants, …) on shared data.
This repository is the single way to validate them, so that every result is comparable and anyone can
pick up anyone else's results.

1. **One contract.** Every model is evaluated on the same data (frozen split files), with the same start
   points and horizons (a frozen protocol file), the same metric code and the same output layout.
2. **Agents run the pipeline; they don't write it.** A user, or their agent (Claude Code, Codex, or any
   other), writes exactly two things: an adapter for their model and a run request. Everything else
   (which dumps, which metrics, every path and filename) is decided by the code.
3. **Same inputs → same outputs.** The same model, checkpoint and protocol must produce the same files
   with the same names. Numbers must be bit-identical on CPU and within a stated tolerance on GPU.
4. **Physical units.** Data, adapter inputs and adapter outputs are physical (unnormalized). Only the
   "loss-space" metrics (section 4) use the fixed TRON normalization. Everything else is physical.
5. **Shared and recorded.** Results live in one group folder on Delta/DeltaAI. Every evaluation,
   including repeated test runs and failed runs, is recorded.

## 2. Data contract (done; frozen)

- `splits/<split_id>.json` (schema_version 2), generated by `splits/make_splits.py`. Never edit one; a
  change is a new version. The structure:
  - `segments`: the whole run in time order.
  - `splits.{train,validation,test,excluded}`: each with `chunks` and per-dump `files`, relative to
    `data_root`.
- v1 layout: three validation and three test chunks at separate positions, with 10 excluded dumps on
  each side of every chunk. See `split_rule` in the file.
- The code reads dumps **only** through the split file. It never lists data directories. Paths are
  `data_root` + file. A `--data-root` override is allowed (for other machines), but the split file's
  identity is its SHA256 and doesn't depend on the path.
- **Per-file checksums.** Owner-run Slurm job `gval checksums --split-file …` writes
  `checksums/<split_id>.sha256`.
  - It hashes **every file listed in the split file**: train, validation, test **and** excluded, plus
    `geometry.npz`. The geometry hash is checked against the split file's `geometry_sha256`.
  - Format: sha256sum, one line per file, path relative to `data_root`, sorted by dump ID.
  - Evaluation verifies the SHA256 of every dump it reads against that file. It fails if a hash is
    missing or wrong, unless `--no-verify-data`, which is recorded in `run.json` and marks the run
    unverified.
- **What "excluded" means.** The split files say excluded dumps must never be used. That rule is about
  **models**: an excluded dump is never a training sample, an input, a target or an evaluation sample.
  Whole-run *truth* tools may still read excluded dumps, because they never feed a model:
  - checksums;
  - the data movies and timeline (`docs/specs/movies.md`).

  The runner and the adapter API never pass an excluded dump to a model. A test asserts this.
- Known data issue (recorded in the split files): rc300 cells with r < 6.11 are a coarse AMR level, each
  value duplicated into 2 × 2 × 2 cells. 5000run uses only the main-folder dumps; `blind/` is outdated.

## 3. Evaluation protocol

`protocols/forecast_v1.json` holds every setting below. The runner reads it; nothing in it is a CLI flag.

### 3.1 What a model is given and scored on

- **Eligible windows.** Evaluate only on validation or test chunks. Every history frame, start frame and
  target frame of a sample lies inside **one** chunk.
- **History.** At start dump s, the adapter receives the true frames `s − h + 1 … s`, where h is the
  adapter's `history_length` (1 ≤ h ≤ `H_max`). It receives nothing later than s.
- **Same starts for every model.** In each chunk, eligible starts are
  `[chunk_first + H_max − 1, chunk_last − max_steps]`, whatever h a model uses.
  - `H_max` = 10.
  - Single-step metrics use every eligible start.
  - Rollout analyses use `n_starts_per_chunk` starts, evenly spaced over the eligible range:
    `round(linspace(lo, hi, n))`, de-duplicated.
- **Rollout.** Autoregressive. After step 1, the adapter's own outputs become its history, mixed with
  the true frames still inside the window, i.e. the standard rolling buffer. The runner, not the
  adapter, keeps that buffer.
- **Horizon.** `max_steps` = 50 steps, scored at `report_steps` = 1, 10, 25 and 50 (Kevin's
  defaults).

### 3.2 Analyses (all from Kevin's suite, `Fall26/eval/evaluate_forecast_ds.py`)

The protocol lists which analyses run in each tier; v1 runs all of them.
Tiers:
- `quick`: single_step, rollout_curve. Minutes; used during development.
- `full`: every analysis listed in the protocol. Required for the leaderboard.

|---|---|

### 3.3 Quick-tier definitions (milestone 2: final semantics, not a temporary port)

Milestone 2 implements single_step and rollout_curve with their **final** v1 semantics, including the
block-bootstrap CIs. Milestone 4 does not revisit them, so the golden made in milestone 2 stays valid.
The other analyses get their improvements in milestone 4.

**Arithmetic.**
- The runner casts truth and prediction to float64 numpy on CPU before any metric. All metric code is
  numpy float64 on CPU.
- Reductions are `np.mean` / `np.sum` over C-contiguous arrays in `[channel, r, θ, φ]` order.
- Kevin's code runs the normalizer in float32 torch. That difference is accepted; the regression
  against Kevin's numbers uses 1e-5 relative for these two analyses.

**Constants.** Add this block to `protocols/forecast_v1.json` under `"constants"`, extend the protocol
schema, and make `read_protocol` validate it. Values are Kevin's unless marked.

```json
"constants": {
  "loss_space": {
    "floor_rho": 1e-20, "floor_ug": 1e-22,
    "transforms": ["log10", "log10", "arcsinh", "arcsinh", "arcsinh", "arcsinh", "arcsinh", "arcsinh"]
  },
  "skill": {"persistence_min": 1e-6, "epsilon": 1e-30},
  "rel_l1": {"denominator_min": 1e-30},
  "growth_curve": {"step1_min": 1e-4},
  "ci": {"percentiles": [2.5, 97.5], "rollout_resample_unit": "start"},
  "active_disk": {"r_max": 100.0, "theta_halfwidth": 0.5},
  "correlation_time": {"r1_clip": 0.999, "r1_saturated": 0.99, "r1_cap": 0.99},
  "attractor": {"sigma_dump_stride": 10},
  "figures": {"backend": "Agg", "dpi": 150, "font": "DejaVu Sans", "font_size": 11,
              "rollout_curve_figsize": [14, 5]}
}
```

**Loss-space transform.**
- `L(x)`: channel 0 → `log10(max(rho, floor_rho))`, channel 1 → `log10(max(ug, floor_ug))`, channels
  2–7 → `arcsinh(x)`.
- It is applied by the benchmark to the truth, the prediction and the persistence forecast.
- No ceilings, no Lorentz clamp. Those belong to the model's own decode, and the output is scored as
  returned.

**single_step** (`metrics/single_step.json`, `tables/single_step.csv`)
- **Samples:** every eligible start s (§3.1) of every chunk of the evaluated split. Target is s + 1.
  Persistence forecast = frame s.
- **Per sample and channel c:**
  - `nmae_model[c]` = mean over cells of |L(pred) − L(true)|.
  - `nmae_persist[c]` is the same with the persistence forecast.
  - `rel_l1[c]` = mean|pred − true| / mean|true| in physical units, or NaN if the denominator is below
    `denominator_min`.
- **Aggregates per channel:**
  - the mean of `nmae_model` and of `nmae_persist` over samples;
  - `rel_l1` = nanmean over samples;
  - `skill` = NaN if `nmae_persist` < `persistence_min`, else `1 − nmae_model / (nmae_persist + epsilon)`.
  - Rows: the 8 channels, then `mean` (nanmean over channels), then `fluid` (channels 0–4) and
    `magnetic` (5–7) for nMAE.
- **CI (block bootstrap):**
  - Within each chunk, cut that chunk's ordered starts into consecutive blocks of `bootstrap_block`
    starts; the last block may be shorter.
  - Pool all blocks of the split. Draw, with replacement, as many blocks as there are, using
    `np.random.default_rng(seed).integers`.
  - Concatenate the drawn blocks, recompute the per-channel skill (same NaN rule), and repeat
    `bootstrap_resamples` times.
  - CI = `np.nanpercentile` at `ci.percentiles`. Report `n_samples`, `n_blocks` and the method string.
- `summary.json` gets per-channel `nmae_model`, `nmae_persist`, `skill`, `skill_ci`, `rel_l1`, and the
  `mean` row.

**rollout_curve** (`metrics/rollout_curve.json`, `tables/rollout_curve.csv`, `figures/fig02_rollout_curve.png`)
- **Starts:** the protocol rollout starts (§3.1: `n_starts_per_chunk` per chunk, evenly spaced). No
  random selection.
  - If a chunk has fewer than `max_steps` + `H_max` dumps, fail; don't silently shorten.
- **Step k = 1 … max_steps:**
  - per start and channel: `nmae_model[k, c]`;
  - `nmae_persist[k, c]`, using frame s held fixed for every k.
- **Aggregates:**
  - `mean_nmae[k]` = mean over starts of the channel mean;
  - `std_nmae[k]` = population std (ddof = 0) over starts of the channel mean;
  - `mean_persist[k]`;
  - `skill[k]` = `1 − mean_nmae / (mean_persist + epsilon)`;
  - `per_channel[k, c]` = mean over starts.
  - Report all of these at every step in the JSON, and at `report_steps` in the CSV and summary.
- **CI on `skill[k]`:** bootstrap over starts, resampling individual starts (they are ≥ 100 dumps
  apart), with the same seed, number of resamples and percentiles.
- **Attractor saturation:**
  - `sigma[c]` = mean over truth dumps of the evaluated split, taking every `sigma_dump_stride`-th dump
    of each chunk starting at its first, of the per-dump std over cells of L(truth).
  - Flag `ok` if `per_channel[max_steps, c] < sigma[c]`, else `exceeds`.
  - This replaces Kevin's "first 50 dumps of the folder".
- **Figure:** Kevin's two panels.
  - (a) mean nMAE ± std vs persistence.
  - (b) per-channel growth relative to step 1, using absolute nMAE for channels whose step-1 value is
    below `step1_min`, labelled "(abs)".
  - x ticks follow Kevin's `dynamic_xticks`; channel colours follow Kevin's `CHANNEL_COLORS`.
  - Channel labels are the split-file names (`rho … B3`). The legend says "model", not a model name.
- **Not in milestone 2:**
  - the predictability horizon (Table 4) and τ_c, which belong to `correlation_times` in milestone 3,
    using the `correlation_time` and `active_disk` constants above. For rc300 the disk mask
    additionally requires `resolved == True`; the pairs are consecutive truth dumps inside one chunk
    of the evaluated split.
  - every other analysis.

### 3.4 Milestone-3 full-tier port configuration

The original evaluator's non-quick defaults are recorded in constants.full in
forecast_v1.json (source main@ebcc218); numerical guards and fixed plot/table
conventions remain part of each credited computation. The core accepts explicit
metric space and start selection for regression. The milestone-3 production
start policy is single: the first common protocol rollout start, with original
within-analysis pair/statistic sampling restricted to the frozen split. This is
an intermediate port, not the milestone-4 final all-start aggregate/CIs. The all
selection remains a callable core configuration, tested independently and enabled
for final aggregates in milestone 4. No CLI setting may select a more favorable
start or change the metric space.

Outside the loss-space analyses enumerated in §4, production uses physical
fields; legacy loss space is a regression option only. Physical relative errors
and stability perturbations/response use the owner-generated training mean-abs or
RMS channel scale (§4). This change is tested separately from legacy numerical
regression. Do not alter the final milestone-2 single_step/rollout_curve semantics.

Every remaining analysis writes metrics/<analysis>.json and tables/<analysis>.csv
with a closed schema. Numeric arrays, counts and selection/space labels are
result content; paths, times, versions and host information are not. Diagnostic
figures keep fixed figNN_<analysis>.png names, the corresponding original panel
sizes, Agg/150 dpi/DejaVu Sans 11 and no timestamp metadata. Cost parameter counts
and measurement configuration are deterministic result content; measured wall
latency, peak memory and runtime profiling live only in run.json/logs, and are
excluded from fingerprints. Timing measurements cannot be golden numerical
comparisons; their measurement arithmetic is tested using a controlled clock.

The physical structure-function signed third moment uses the same positive lag
on both slices. This avoids the original Python precedence error for odd
maximum lag (`[:-max_lag//2]`); the legacy regression path retains that original
expression. A synthetic linear field tests the physical formula separately.

Adding the full-tier settings changes the protocol file hash but must not change
any quick result bytes. The normal owner reference path can regenerate identical
quick content and refresh its metadata; an unequal quick fingerprint is an error,
not a new golden to accept. No frozen split definitions change.

### 3.5 Milestone-4 publication gate and finalization (owner decision)

Until milestone 4 is complete, full-tier evaluations are previews. The runner
must keep their completed bundles in staging/<user>/<run_id>/, write PREVIEW,
set run.json status to preview with preview_reason, and never write COMPLETE or
create a runs/ destination for them. The CLI returns preview: true and the
staging path; a completed preview is not a leaderboard submission. Quick-tier
publication is unchanged. Failed previews retain the normal FAILED record.
verify identifies previews, and report excludes them even if files are otherwise
valid. Preview attempts still count toward attempt numbering.

The gate is closed unless constants.full.production_ready is explicitly true;
its absence in the milestone-3 protocol means false. During implementation the
committed forecast_v1.json stays unchanged. Final settings, all-start/CIs,
transport/coarse-ring handling, verified owner truth caches and fixed artifacts
are validated before the last milestone-4 implementation step. That last step
updates forecast_v1.json once to the final semantics and production_ready: true,
lifting the gate and changing its SHA256 once. It does not promote any existing
preview or rewrite historical results. Regenerate quick and full persistence
references under the final protocol hash, then rerun both splits' conformance.

The comparison identity is (split_id, protocol_id, protocol_sha256, tier).
Leaderboard/report grouping, verification comparisons and reference/cache
selection must use the protocol SHA256, not protocol_id alone. Results with
different hashes are separate comparison groups, even when both say forecast_v1.

## 4. Metric spaces

- **Loss space.** The fixed TRON normalization, identical to `Fall26/common/normalizer.py`: log10 for
  rho and ug, arcsinh for utilde and B. It is applied by the benchmark to the physical truth and the
  physical prediction, whatever normalization the model trains with. Used only for: nMAE, skill vs
  persistence (single-step and rollout curve), predictability horizon, and attractor saturation.
- **Physical space for everything else.** Error maps, conditional error, bias analysis, error
  correlation, stability (perturbation and output measured in physical units, relative to each
  channel's training-split RMS), distributions, spectra and every physics quantity.
  - For each analysis, the implementer writes `docs/metrics.md`. It gives the formula, the space, the
    units, the averaging, and how it differs from Kevin's original.
  - If moving an analysis from normalized to physical space changes its meaning, flag it for review.
- Physical relative errors need a reference scale. Use the training-split per-channel mean of |x| or
  RMS, computed once by the owner into `references/<split_id>/channel_scales.json` from training dumps
  only. Every run uses this file.

The owner creates these scales on a compute node with
`gval reference channel-scales --split-id <id>`. The closed-schema JSON records
`split_id`, `split_file_sha256`, `data_manifest_sha256`, the eight `channels` in
split order, `n_dumps`, `n_cells_per_channel`, arrays `mean_abs` and `rms`, and
`data_verified: true`. Every cell of every training dump has equal weight.
Reductions use float64 NumPy in dump-ID order; RMS is sqrt(sum(x*x)/N), not the
standard deviation. Checksums are mandatory. No validation, test or excluded
dump contributes. An existing unequal file is an error; an identical file is
reused. Full-tier runs verify its split identity and record its SHA256 in
run.json. This truth-only owner command creates only references/<split_id>/.

### 5.10 Final all-start statistics and truth-cache contract

Full-tier rollout diagnostics use every common rollout start from §3.1. Preserve
per-start values and report equal-weight start means with pointwise 95% CIs.
Resample bootstrap_block consecutive selected starts within each chunk, retaining
the last short block, and draw the original number of pooled blocks with
replacement. With four rollout starts per chunk and block length ten, each
chunk contributes one short block. The existing seed/resample count/percentiles
apply. Quick-tier statistics retain §3.3 exactly.

Nonlinear statistics are recomputed on each resample: error-correlation matrices
use the sampled single-step error vectors; conditional-bin errors use summed
absolute errors divided by summed bin counts; bias RMS uses the square root of
the mean squared phi-mean errors; predictability horizons use skill from the
start-mean model/persistence errors. Correlation-time truth estimates remain a
fixed shared reference during the forecast-start bootstrap. Coordinates, channel
IDs, step axes and model parameter counts are invariant/degenerate intervals,
not noisy measurements. Timing CIs belong only in run metadata.

Each full analysis retains data.per_start and adds data.aggregate with mean,
lower, upper, n_starts and bootstrap (method, block length, block count, resample
count and seed). Conditional error and error correlation use every common
single-step start; the other diagnostics use all common rollout starts. Figures
show these aggregate values and curve CIs; map CIs remain in JSON/CSV. Physical
states/profiles are averaged before any display logarithm. Histogram edges are
fixed from the pooled truth at the analysis horizon, and conditional-bin edges
use the original seeded truth-only sampling rule. No model prediction sets the
shared bins. A source regression continues to use the original sampling/bins.

Aggregate figure presentation retains Kevin's panel designs, physics titles,
channel names, axis units and logarithmic scales. Each displayed truth/model
curve has one mean and one 95% CI band; only panels designed for multiple
report steps show those steps. Step labels give the actual step and elapsed
time from dt_dump, for example step 10 (1,000 R_g/c), never an array index.
Use shared role/channel/step colours and a caption naming the start count and
evaluated split and identifying bands as 95% CIs. Every visible data axis has
physics labels; internal result keys are forbidden in titles and legends.
Figure-only regeneration may read existing verified result content without
inference and writes a separate presentation bundle. Attach an rc300 contact
sheet of every full-tier figure to the milestone-4 receipt for visual review.

For panels overlaying multiple report steps, plot both roles' means at every
report step (truth solid, model dashed, one shared colour per step), but draw
only the final report step's 95% CI bands: one per role, light and without an
outline. Error/ratio overlays similarly show a band only at the final step.
The caption states the start count, final band step, split and the metric JSON
containing all intervals. The dimensionless-flux time-series panel keeps one
line and one band per role across all its steps. Other time series, single-step
panels and maps retain their original designs. This is presentation only;
all per-step means and CIs remain in the metric artifacts.

The owner may refresh derived PNGs in an existing persistence reference only
after verifying its unchanged result-content fingerprint. Replace PNGs
atomically with group-readable owner files and record presentation hashes;
the metric/CSV/summary files and golden fingerprint are unchanged. Keep the
versioned review bundle as the presentation receipt. This permission applies
to owner persistence references, not completed model runs.

Non-negative physical error maps (absolute errors and RMS) use LogNorm, with
limits at the 1st and 99.5th percentiles of positive finite cell values whose
centres lie in the displayed region. Zero/non-finite values are uncoloured;
the underlying arrays are unchanged. All-zero or unavailable maps are labelled
explicitly. A degenerate positive percentile range uses one decade centred on
that value. Signed bias maps use SymLogNorm centred on zero: the symmetric
bound is the 99.5th percentile of nonzero absolute values and the linear
threshold is their 1st percentile, again within the displayed region. Every
error colourbar names its units and log scale (symmetric log for bias).
Presentation tests reject a nonconstant visible map if over 90% of its
unmasked cell values occupy the lowest 5% of the colour range. Figure-only
receipts record the normalization, bounds, visibility and contrast checks.

Owner command `gval reference truth --split-id <id> --split validation|test`
builds the verified truth/persistence cache. It writes only under
references/<split_id>/<protocol_id>/<protocol_sha256>/, mode 2750, with separate
partition identity. The cache contains correlation times, truth spectra/shell
profiles, fixed bin edges and persistence baseline errors. It contains no learned
model predictions. Its manifest pins the frozen split/geometry/checksum-manifest
hashes, partition, protocol hash, cache schema, entry hashes and cache-file hash.
The manifest also binds the training channel-scales SHA256 used by physical
persistence baselines. Entries use pickle-free NumPy serialization. Readers are strictly read-only and
reject missing/corrupt/mismatched caches. run.json records the cache hash; cache
metadata is excluded from result fingerprints. Only the owner on a compute node
may create a missing cache, and an existing verified cache is reused.

Memory is bounded independently of the number of forecast starts: reduce one
start at a time, release its volume fields before the next, and retain only
reduced profiles, spectra, maps and scalars in per-start result rows. Store
prediction states as float32; materialize float64 only for the reduction that
needs it. Build disk caches incrementally. Sequential scratch/data I/O must not
retain a run-sized file cache in the Slurm memory cgroup. Record per-analysis
process RSS and allocation memory outside deterministic result content. The
5000run full reference and conformance must each stay within 48 GB, verified
with sacct MaxRSS under the existing 64 GB allocation. These implementation
changes must preserve existing result fingerprints and the protocol hash.

The final owner persistence reference supports --tier quick|full. Golden/cache
selection includes the protocol SHA256 directory, so previous hash cohorts are
not overwritten. Before finalization, the unchanged milestone-3 quick reference
location remains readable only when its recorded hash matches. Conformance
supports either tier, and the CLI defaults to checking both tiers once the
protocol is final (quick only while gated). A production full evaluation requires
passing full-tier conformance for its platform/lock/split/protocol hash.

### 5.11 Production transport signs and efficiencies (owner option 4)

Use geometry dx[1]*dx[2] as the angular coordinate area element, including
sqrt(-g) in every shell integral. All accretion fluxes are positive inward:
Mdot = -integral rho*u^r*sqrt(-g) dA;
Edot = +integral T^r_t*sqrt(-g) dA (total energy, including rest mass);
Ldot = -integral T^r_phi*sqrt(-g) dA.
The total efficiency is eta = (Mdot-Edot)/Mdot on the same shell and step.
P_jet = -integral_funnel (T^r_t+rho*u^r)*sqrt(-g) dA removes rest-mass flux;
eta_jet = P_jet/Mdot on that same shell/step. Efficiencies are undefined for
Mdot <= 0: emit null and nonpositive_mass_inflow as the reason, never |Mdot|.
Across starts, preserve per-start reasons and report finite-sample counts along
with nanmean/CIs; an entirely undefined quantity has null mean and CI.

Use Kevin's funnel mask (magnetization, polar cut, outflow/energy-flux condition,
and density guard), but use the rest-mass-subtracted production jet power.
Compute u^t from the normalization with the metric, reconstruct coordinate u^r,
u_t and u_phi, and form the ideal-MHD stress tensor with fluid-frame b^mu.
Audit the normalization and flux components in a nonzero-shift synthetic metric.
Cold marginally bound radial inflow with u_t=-1, u_phi=0, ug=B=0 must give
Edot=Mdot, eta=0 and Ldot=0. A moving Minkowski flow also carries kinetic energy
and is not that oracle.

Report horizon and first-resolved-shell quantities. For rc300 the horizon
record is flagged coarse_ring and the headline selects the first wholly
resolved shell at r>=6.11. Preserve Kevin's original rest-mass-inclusive P_jet
and eta=P_jet/|Mdot| only in the explicit legacy regression path.

The final protocol records these fixed conventions in constants.full.transport,
coarse_ring_r_min=6.11 and jet_density_floor_multiple=100. The existing
milestone3_start_policy becomes all; production_ready becomes true only at the
last implementation step. constants.figures.full_figsizes maps each analysis to
the original figure sizes in fixed output order (including each zoom/variant).
These additions are applied together, changing the protocol-file hash once.

## 6. Plugging in a model (adapter contract)

A user keeps their model code in their own repository. They add one adapter file and never touch this
repository's code.

```python
from grmhd_validation import ModelAdapter, Geometry

class Adapter(ModelAdapter):
    name = "tron"              # [a-z0-9-]+, unique on the leaderboard
    version = "v1"             # bump when architecture/training changes
    history_length = 1         # frames needed, 1..H_max
    max_batch = 1              # starts the runner may batch together

    def __init__(self, checkpoint: str, geometry: Geometry, device: str, options: dict):
        ...                    # load weights; restore the model's own normalization from the checkpoint

    def step(self, history):   # torch.float32 [B, h, 8, Nr, Nθ, Nφ], physical, on `device`
        ...                    # return torch.float32 [B, 8, Nr, Nθ, Nφ], physical

    # optional: override if the model predicts several steps at once
    def rollout(self, history, n_steps):   # -> [B, n_steps, 8, Nr, Nθ, Nφ]
        ...
```

- `Geometry` provides r, θ, φ, the metric, gdet, dx, spin, dt_dump and `resolved` as tensors. It
  contains no data paths: adapters get data **only** as arguments.
- The adapter does any normalization, clamping, floors or Lorentz limits itself. **The output is scored
  as returned**; any non-finite value or wrong shape or dtype fails the run.
- The adapter is referenced as `/abs/path/adapter.py:Adapter`, or as an installed entry point in group
  `grmhd_validation.adapters`.
- Its source SHA256, and the git commit of its repository if there is one, go into `run.json`.
- Ship `adapters/persistence/` (h = 1, returns the last frame) and `adapters/tron_example/`, ported from
  `Fall26/eval/evaluate_tron.py` on branch `fall26-tron-rc300`, as references.
- Helper commands:
  - `gval new-adapter <dir>` writes a template adapter plus `run_request.json`.
  - `gval check-adapter <ref> --checkpoint …` runs on a few validation dumps. It checks shapes, dtype,
    finiteness, that two calls give identical output in eval mode, that `history_length` is honoured,
    and memory and time per step. It prints a JSON verdict.
- **Run request** (`run_request.json`, the only other user-written file):
  `{model: name, version, adapter: ref, checkpoint: path|null, options: {}, training_record: path|null, notes: ""}`.
- **Models without weights.** An adapter class declares `requires_checkpoint = True` (the default) or
  `False`. Persistence declares `False`.
  - With `False`, the request must have `"checkpoint": null`. A path is an error, so nobody can attach
    a meaningless file.
  - With `True`, `null` is an error.
  - With no checkpoint: `run.json` has `checkpoint_sha256: null` and `checkpoint: null`; the run_id
    token is the literal `nockpt`; `ckpt_sha8` is shown as `nockpt` everywhere.
  - Example: `persistence-v1__nockpt__rc300_reduced_v1__validation__quick__a1`.
  - The adapter source SHA256 is still recorded, so persistence runs remain identifiable.
- Docs: `docs/plugging_in_a_model.md`, a step-by-step walkthrough with the TRON example.

## 6.1 Agent-driven prediction mode (milestone 5)

This section specifies milestone 5, not an additional milestone-3 analysis.
Prediction mode feeds the same scorer as adapters. It does not change the frozen
splits, common starts, horizons, physical tensor contract or metric definitions.
A prompt or agent-provider change does not create a new data split.

### Roles and access

| Role | Responsibility | May see |
|---|---|---|
| Forecasting agent | Produce forecasting code (A), or the active one-step prediction (B). | Only its exported packet, its prompt, allowed tools and its own submission. |
| Host | Create tasks/packets, enforce the history boundary, freeze outputs, advance the rolling buffer and collect submissions. | Frozen split/configuration and source data needed to construct allowed histories; never send future truth or scores to the forecasting agent. |
| Scorer | Validate collected predictions and compute common metrics/figures. | The frozen predictions, provenance, geometry and truth from the evaluated split. |

The host and scorer may be the same operator, but the forecasting agent must be a
separate generation session with only the packet workspace exposed. Opening the
whole benchmark/data repository in that session is forbidden. Packet creation
must materialize allowed arrays, not symlink to a parent data tree. The host
records the actual isolation mechanism and any exceptions; a directory name or
an agent's self-report is not evidence of enforced isolation. Results without a
complete host attestation are labelled unattested, not claimed as blind results.
Neither tools, transcripts nor packet metadata may expose API credentials.

### Two protocols

- **A — code generation.** The agent writes a reusable one-step method from its
  packet. The host freezes its source and wraps it as a ModelAdapter (§6). The
  host runs that fixed code for every required start and all 50 steps. The agent
  is not consulted again during those rollouts. The runner owns history and
  scoring; data paths, truth lookups and changes of method between starts are
  forbidden. Code changes require a new model version and recorded attempt.
- **B — stepwise generation.** The agent produces exactly the active step. The
  host freezes and validates it, advances using that prediction, then gives the
  next packet to the agent. There are 50 accepted generation steps per rollout
  start. A request for step k cannot receive truth for steps 1..k, including as
  feedback, a correction or an example. Code-only host rollouts must not be
  described as B.

Record protocol A or B explicitly. They are distinct methods even when provider,
model and prompt are otherwise equal. Protocol A may use normal adapter evaluation
and may also export a prediction bundle. Protocol B uses collected predictions.
For B, inference-cost and perturbation/stability metrics requiring an executable
adapter are `not evaluated` with a reason; generation wall time is provenance,
not a substitute for model inference cost. No placeholder zeros are scored.

### Task, packet and scoring commands

All commands set umask 007 and return the standard final JSON verdict (§12).
Task/packet paths below are user-owned workspaces outside shared validation
storage; they do not add a new top-level shared-folder area. Only evaluate writes
a benchmark attempt using the existing staging/publish/seal lifecycle (§7).

```bash
# Host: freeze the request and all required start/target identities.
gval task --request run_request.json --split-id <id> --split validation|test \
  --protocol A|B --prompt-id <prompt_id> --output <task_dir>

# Host: export one isolated start/step; S must belong to task.json.
gval packet create --task <task_dir> --kind rollout|single_step --start S \
  --output <packet_dir>

# Host: validate/freeze the active submission and advance using its prediction.
gval packet advance --task <task_dir> --packet <packet_dir>

# Host: validate and collect frozen outputs into the fixed bundle layout.
gval packet collect --task <task_dir> --output <prediction_bundle>

# Scorer: no model-specific metric or figure path.
gval evaluate --request run_request.json --predictions <prediction_bundle> \
  --split-id <id> --split validation|test --tier quick|full
```

`task` reads the committed protocol and frozen split and writes immutable
`task.json`: task/schema IDs, request hash, split/protocol/geometry hashes,
partition, protocol A/B, prompt identity/hash, history length, all required start
IDs grouped by chunk, every required target ID/step, expected shape/dtype/channel
order, seed, and completeness rules. Its identity is its SHA256. The host keeps
source paths and truth manifests separately; they are not exported to agents.
There is no CLI option to shorten the horizon or select a benchmark subset.
Creating one packet at a time is scheduling, not permission to reduce coverage.

`packet create` follows Eden's episode contract: README.md, prompt.md, format.md,
output_schema.json, episode.json, inputs/geometry.npz and inputs/current_state.npy,
plus inputs/history.npy when h > 1. Arrays are physical float32; history is
[h,8,Nr,Ntheta,Nphi], current_state equals its last frame. Geometry and shape are
from this dataset, with no hard-coded rc300 dimensions/cadence. episode.json names
task/episode/prompt IDs, chunk/start, kind, active_step, required_steps,
required_prediction_files, input hashes and state_from_step. A fresh agent
context is required for each independent start/single-step sample. Within a B
rollout the declared prompt template fixes fresh-per-step versus continued-per-
start sessions; record the actual session IDs. Never carry one start's true
history into another start's generation context.

The agent writes only submission/prediction_step_XXXX.npy for the active step,
submission/submission.json, and any reproducible source under submission/code/.
It may read only allowed packet inputs; it does not call advance, collect or the
scorer. Unlike Eden's original permissive dtype list, this benchmark requires
finite float32 of exact shape [8,Nr,Ntheta,Nphi], with allow_pickle=False and
channels rho, ug, utilde1, utilde2, utilde3, B1, B2, B3. The host does not cast,
clamp, repair, interpolate or silently replace submitted values.

`advance` validates task/episode/step identity and input hashes, freezes the file
and its metadata by hash without overwrite, then advances active_step. The new
history is the standard rolling buffer: remaining initial history plus accepted
predictions; no later truth is inserted. An accepted step cannot be replaced by
a retry or by a scorer's preferred candidate. Rejected attempts and their reasons
are recorded. Generation may resume an interrupted task from its last frozen
step only if the chain of input/output hashes still verifies.

`collect` checks the whole frozen chain and copies only verified frozen outputs
into the bundle. It emits an explicit coverage manifest listing required,
received, missing and invalid entries. It never pads a chain, repeats a missing
file, uses persistence for a missing step or averages multiple submissions.

### Fixed prediction bundle

`<chunk>` is the frozen chunk name; `<s>` is the decimal start dump ID. Filenames
use Eden's four-digit step numbering, independent of absolute dump ID.

```text
<prediction_bundle>/
  task.json
  predictions.json                 coverage, paths and SHA256 of every entry
  provenance.json                  per-run generation/host provenance
  host_attestation.json
  code/                            frozen source for A; optional reproducible B tools
  rollout/<chunk>/start_<s>/
    prediction_step_0001.npy        all steps 0001..0050, one physical cube each
    ...
    prediction_step_0050.npy
    steps/step_0001.json            one immutable provenance record per step
    ...
    steps/step_0050.json
  single_step/<chunk>/start_<s>/
    prediction_step_0001.npy
    steps/step_0001.json
```

Paths are relative, canonical and confined to the bundle. No symlinks or pickle
objects are accepted. The scorer verifies file hashes, shapes, dtype, finiteness,
task/request identities and the autoregressive input/output chain before scoring.
Both adapters and prediction files supply identical physical states to the same
analysis modules; imported predictions must not introduce an alternate metric
implementation. The collected bundle and its provenance hashes go in run.json.
Run-specific provenance never enters summary/metric/table result content (§11).

### Completeness and `not evaluated`

- All **12 rollout starts** (four per each of the three evaluated chunks) and
  **all 50 steps per start** are required: 600 distinct required entries. The
  authoritative IDs come from §3.1, not Eden's historical starts or a hand list.
- If any required rollout entry is missing, invalid or unverified, rollout
  analyses are **not evaluated**. Report exact missing/invalid (chunk,start,step)
  entries; do not score the available subset or shorten to a common prefix.
- Single-step is evaluated only when **every** eligible common start in every
  chunk is present with a valid s+1 prediction. Fifty-step rollout step-1 files
  cover only the 12 rollout starts and do not stand in for the complete
  single-step set. Shared files may be referenced only when the input histories,
  task/prompt/protocol provenance and output hashes are identical.
- Coverage is explicit for each analysis. A valid complete rollout may produce
  rollout diagnostics while single-step is `not evaluated`; this does not make
  an incomplete quick/full request eligible for the corresponding leaderboard.
  Any requested analysis lacking required inputs is marked `not evaluated`, with
  metric values null/absent and a reason, never zero or a misleading mean.
- An incomplete attempt is recorded in staging with status `not evaluated`, a
  NOT_EVALUATED marker and its coverage diagnostics; no COMPLETE or successful
  benchmark verdict is written. Inspection artifacts for eligible analyses are
  clearly labelled partial and are not published as a complete run. Completing
  the task requires a new recorded evaluation attempt; earlier attempts remain.

### Versioned prompts and provenance

Prompt templates live in `prompts/<prompt_id>/` with template.md and manifest.json.
A prompt_id is immutable and versioned. Its manifest records the source packet
contract/commit, protocol A/B, session policy, allowed tool/network access, input
and output schema versions, rendering fields and template SHA256. Template
changes, provider-specific additions or changed session policy require a new
prompt_id; neither the agent nor host may silently edit the rendered prompt.
Store both template and rendered-prompt hashes. The initial A/B templates adapt
Eden's `primary_ar_onestep` packet/prompt, with attribution, dynamic grid/cadence,
the benchmark's h-frame history and strict float32/coverage rules.

Per-run provenance records task/request/split/protocol/geometry hashes; protocol
A/B; prompt_id and hashes; forecasting provider, actual model identifier/version,
agent client/version, declared generation parameters and seed (null if unavailable);
source repository/commit and code/checkpoint hashes; training record and known
prior data exposure; allowed/actual tool and network access; transcript/tool-log
hashes; host/scorer identity, host/job, environment lock and code commit;
start/end times and submission/collection identities. Never infer a provider
version, seed or isolation claim from a model nickname.

Per-step records contain episode/task IDs, chunk/start/target ID, step,
active_step, input-history and geometry hashes, previous frozen-output hash,
rendered-prompt hash, session/request/response IDs, actual provider/model,
code hash for A or tool-code hashes for B, prediction path/hash/shape/dtype,
generation/freeze times and elapsed generation time, transcript/tool-log hashes,
rejections/retries and the host's validation result. Unknown fields are explicit
null with a reason; required file/history identity fields cannot be unknown.

The host attests, against the collected manifest hash, to the actual workspace
and access controls; permitted history only; absence of future truth, evaluator,
other starts and scorer feedback in generation sessions; context/session policy;
autoregressive advancement from frozen predictions; source and prompt freezing;
and complete collection without selection or replacement. It names the operator,
host/job, implementation commit, logs and attestation time. Missing evidence or
exceptions remain visible as unattested/exposure flags; scorer output must not
claim a blind experiment on the basis of an unchecked agent statement.

Role-specific instructions are separate deliverables: forecasting instructions
inside each packet; host instructions for task/create/advance/collect and audit;
scorer instructions for completeness, evaluate --predictions and reporting.
Benchmark-repository instructions are not the forecasting-agent prompt.

### Implementation formats and audit boundaries

Task and packet schemas are version 1. The initial immutable prompt IDs are
`eden-code-v1` (A, fresh context per start) and `eden-step-v1` (B, fresh context
per step). They permit local Python/NumPy/SciPy tools and no network. New access
policies use new prompt IDs. Provider/model/session details are host-supplied
metadata, never guessed from the request model name.

The host workspace stores private `host.json` and `episodes/` beside task.json;
only the packet directory is exposed to the forecasting agent. For B, the
request options declare `history_length`; for A it comes from the adapter.
`packet create` writes blank `submission/submission.json` metadata for the agent
and a separate host `generation.json` template, which must be completed before
advance. The latter carries actual session/provider/model identifiers, timing,
logs and explicit unknown reasons. Host run provenance and attestation templates
are outside the packet, at `provenance.json` and `host_attestation.json` in the
task workspace. Attestation evidence is checked structurally and hashed; the
scorer labels claims as host-attested, never independently proven isolation.
Unknown or missing evidence yields unattested status.

Each accepted step is copied under the private task episode and made read-only.
Input arrays and rendered prompt are reconstructed from frozen history before
advance; a modified packet input or prompt is rejected. Every rejection is an
append-only, separate audit record. Advancing an episode updates only the host's
packet inputs and active-step metadata; accepted outputs cannot be overwritten.
Collect records missing coverage without manufacturing predictions. It validates
both file hashes and the complete history chain again. The scorer additionally
binds each initial history to checksum-verified truth. A changed task, frozen
output, provenance record or manifest invalidates that entry.

For imported predictions, cost and stability are not evaluated because no
executable adapter was measured. An incomplete request is retained as a sealed
NOT_EVALUATED staging attempt, with per-analysis reasons in coverage.json; only
eligible analyses may have partial inspection outputs. No successful COMPLETE
marker or runs/ publication is allowed. This also applies to a complete B bundle
requesting the full tier, whose adapter-only analyses remain unavailable.

## 7. Running and outputs

- Commands:
  - `gval evaluate --request run_request.json --split-id <id> --split validation|test --tier quick|full`.
  - Slurm wrappers: `scripts/evaluate_delta.sbatch` (A100) and `scripts/evaluate_deltaai.sbatch`
    (GH200).
- **run_id** is decided by the code:
  `<model>-<version>__<ckpt_sha8>__<split_id>__<split>__<tier>__a<N>`, e.g.
  `persistence-v1__nockpt__rc300_reduced_v1__validation__quick__a1`.
  - The split_id is part of the name, so attempts on different datasets or split versions never share
    a counter.
  - N is the attempt number: 1 + the number of existing directories whose name has the same prefix
    (everything before `a<N>`), complete or not.
  - Count only in `runs/<split_id>/<model>/` (one level) and `staging/*/` (one level). Never walk into
    run directories, so the cost doesn't grow with the number of files.
- Every attempt keeps its directory, so repeated test runs are visible (test discipline = **record**).
- Layout of one run (exact names):

```
runs/<split_id>/<model>/<run_id>/
  run.json          request, attempt, user, host, GPU, CUDA/torch/numpy versions, env lock SHA256,
                    this repo's commit, adapter SHA256 + repo commit, checkpoint SHA256,
                    split file SHA256, protocol SHA256, data verified (bool), start/end time
  summary.json      headline numbers for the leaderboard (fixed schema)
  metrics/<analysis>.json         one per analysis
  tables/<analysis>.csv           where an analysis has a table
  figures/figNN_<analysis>.png    fixed list per protocol
  out_res.txt       human-readable rendering of metrics/
  logs/evaluate.log
  checksums.json    SHA256 of every file above
  COMPLETE          written last, only if everything succeeded
```

- The runner writes into `staging/<user>/<run_id>/`. On success it publishes in this order:
  1. Write every result and metadata file, then `checksums.json`, then `COMPLETE`.
  2. **Freeze the contents.** Remove write permission from every file and subdirectory *inside* the
     run root, working bottom-up. The run root itself stays writable. Linux needs write permission on
     a directory to `rename` it into a different parent, because its `..` entry changes; a subdirectory
     inside it doesn't need it.
  3. **Publish.** `rename` the run root into `runs/<split_id>/<model>/<run_id>`. This is atomic on the
     same filesystem and must not replace an existing target (check first; fail if it exists).
  4. **Seal.** Remove write permission from the run root itself.

  A run whose root is still writable after step 3, for example because of a crash between steps 3 and
  4, is **unsealed**:
  - `gval verify` reports it, and `gval report` lists it as unsealed and leaves it off the
    leaderboard.
  - The run's owner fixes it with `gval seal <run_dir>`. That command only removes write permission
    from the root, and only if the caller owns the run, `COMPLETE` exists, every entry inside is
    already read-only and `checksums.json` verifies. It is the one allowed exception to the rule
    "chmod only what this invocation created".
- On failure the directory stays in staging with `FAILED` and the traceback. It still counts as an
  attempt.
- `gval verify <run_dir>` re-checks the checksums, the schemas and the split/protocol hashes.

## 8. Shared folder and permissions (created; owner gkerex, group delta_bgun)

```
/work/nvme/bgun/share/validation/          2750, group read-only
```

- Owner-only directories have ACLs `g::r-x` plus the same as default.
- Group-writable directories inherit default ACLs `g::rwx`, so files are group-readable whatever a
  user's umask is.
- **Every** `gval` command sets `os.umask(0o007)` as its first action, before any import that might
  write files.
- Directories are created lazily, only by the command that writes into them, with mode 3770
  (setgid + sticky) and group `delta_bgun`:

  | Command | Creates (if missing) |
  |---|---|
  | `evaluate` | `staging/<user>/` at start. `runs/<split_id>/` and `runs/<split_id>/<model>/` only at the final rename of a COMPLETE run |
  | `conformance` | `staging/<user>/conformance/` only; never anything in `runs/` |
  | `reference` (owner) | `references/<split_id>/forecast_v1/persistence_<tier>/<platform>/`, mode 2750 |
  | `record-training` | `training_records/<model>/` |
  | `checksums`, `report`, owner reference jobs | nothing new under the group areas. They write into owner-only areas (`checksums/`, `reports/<split_id>/`, `references/<split_id>/`), creating `<split_id>/` with mode 2750 |
  | `doctor`, `verify`, `check-adapter`, `new-adapter` | nothing in the shared folder (`new-adapter` writes only to the user's target directory) |

- `<user>` is the login name (`getpass.getuser()`).
- Completed runs are frozen in the order of §7: freeze the contents, rename, then seal the root.
- `gval` never runs `chmod` on anything it didn't create in the same invocation. The one exception is
  `gval seal` (§7).
- **Agents never copy files in by hand** (`cp`/`rsync` from a home directory keeps 600 permissions);
  only `gval` writes here.
- `gval doctor` is read-only:
  - It checks the group and the expected modes of the top-level directories.
  - It checks write access to `staging/` with `os.access`; it does not test with a real file.
  - It reports any file in the tree that the group can't read.

## 9. Training provenance (record, not required)

- `gval record-training --request run_request.json --split-id <id> --config <training config> [--log …]`
  writes `training_records/<model>/<ckpt_sha8>.json`.
- It records: split file SHA256, the chunks used for training and for checkpoint selection, where the
  normalization statistics were fitted (must be train), the training code commit and the config.
- `run.json` links it. The leaderboard shows "trained on this split: yes / no / unknown".

## 10. Reporting and the leaderboard

- `gval report --split-id <id>` (owner only):
  - reads every `COMPLETE` run;
  - verifies it;
  - writes `reports/<split_id>/leaderboard.{json,csv,md}` and comparison figures (rollout curves of all
    models, skill bars).
- One row per run. Columns:
  - headline skill and nMAE (loss space);
  - physical relative errors per channel;
  - key physics errors;
  - number of test attempts for that model and checkpoint;
  - data verified;
  - training provenance.

  Rows are sorted by model, then run_id. Numbers have fixed formatting.
- Only compare rows with the same `split_id`, `protocol_id`, `protocol_sha256` and tier. The report states this rule.
- **GitHub.**
  - The owner commits `reports/<split_id>/leaderboard.md`, the comparison figures and each run's
    `summary.json` + `run.json` (under `results/<split_id>/<model>/<run_id>/`) through a PR.
  - CI checks the schemas and that `leaderboard.md` is exactly what `gval report --from-results`
    regenerates from the committed results. Nobody edits it by hand.
  - Full bundles stay on Delta.

## 11. Reproducibility

- **Environment.** Locks are *recorded* from real environments, never written by hand. There is one lock
  per platform, because Delta (x86_64, A100) and DeltaAI (aarch64, GH200) cannot share binaries.
  - `environment/requirements.in`: direct dependencies with lower bounds only. The implementer writes
    it in milestone 1 with exactly these bounds, and the same bounds go into `pyproject.toml`:

    | Package | Lower bound | Why |
    |---|---|---|
    | python | 3.10 | `match` and `X \| Y` types allowed; DeltaAI system Python is 3.10/3.11 |
    | numpy | 1.24 | code must also run on numpy 2.x; test both |
    | scipy | 1.10 | |
    | matplotlib | 3.7 | |
    | torch | 2.3 | `torch.load(weights_only=…)`, deterministic-algorithms API |
    | jsonschema | 4.18 | |

    - No upper bounds; the per-platform lock does the pinning.
    - Analyses ported in milestone 3 may add a dependency only with planner approval, and each needs a
      lower bound and a reason.
    - **The base environment's torch, numpy, scipy and matplotlib must never be replaced by pip.**
      Install this package with `pip install --no-deps -e .` on top of the module, then install only the
      missing packages (e.g. jsonschema) individually.
    - `record_lock.sbatch` fails if any installed version is below the bounds above, or if pip would
      change a base-environment package.
  - `environment/platforms.json`: per platform, how the base environment is loaded. **Owner decision
    (2026-11-15): never use `pytorch-conda`.**
    - `deltaai-aarch64` (the primary platform), following the owner's own DeltaAI job scripts:
      - `module load python/anaconda3/2.15.0`. That is NCSA's Miniforge PyTorch 2.15.0, CUDA 13.2,
        Python 3.12, scipy included. Always pin the full version, never the bare `python/anaconda3`.
      - Then `source "$(conda info --base)/etc/profile.d/conda.sh"; conda activate base`.
      - Don't `module purge` before loading it; its extensions need the default cudatoolkit module.
      - On top of it, a venv created with `python -m venv --system-site-packages <venv>`. Into it go
        only `pip install --no-deps -e <repo>` and any missing package, e.g. `jsonschema>=4.18`.
      - `platforms.json` holds the module, the activation lines and the venv recipe. The venv path is
        per user and is not stored in it.
    - `delta-x86_64`: `null` (not supported) until the owner names a base environment.
  - `scripts/record_lock.sbatch <platform>`: run by the owner on a compute node of that machine. It
    loads the base environment, installs this package, and writes `environment/<platform>.lock`. The
    lock holds the Python version, torch version + CUDA version, and `pip freeze --all` sorted. The
    owner commits it.
  - `gval doctor`:
    - **no lock for the current platform:** status `warn` with `"environment_locked": false`. Doctor
      still succeeds, so milestones 1–2 can proceed.
    - **lock present:** a mismatch in python, torch, CUDA, numpy, scipy or matplotlib is a **fail**;
      any other package mismatch is a `warn`.
  - When comparing pip_freeze, exclude only this package's own editable entry
    (grmhd-emulator-validation); keep the recorded lock unchanged. Its source
    commit is already in run.json. Other editable/package differences still warn,
    and python/torch/CUDA/numpy/scipy/matplotlib mismatches still fail.
  - `run.json` records the platform, the lock SHA256 (or null) and `environment_locked`. The leaderboard
    shows runs from unlocked environments as "unlocked"; the owner's dry run (milestone 7) requires a
    lock.
- **Determinism.** Fixed seeds from the protocol, `torch.use_deterministic_algorithms(True)` where
  supported, eval mode, no autocast unless the adapter enables it (recorded).
- **Golden conformance.**
  - **Result content vs run metadata.** Every run's files fall into two groups.
    - **Result content** (deterministic): `summary.json`, `metrics/*.json` and `tables/*.csv`. These
      files must not contain anything run-specific: no timestamps, run_id, attempt, user, host, paths,
      durations or versions. JSON is written with `sort_keys=True`, `indent=1`, `allow_nan=False` and
      a trailing newline, with floats in Python `repr` (shortest round-trip). CSV uses `\n` line
      endings and `repr` floats.
    - **Run metadata** (varies by design): `run.json`, `logs/`, `checksums.json`, `out_res.txt`,
      `figures/`, `COMPLETE`.
  - **Result fingerprint.** `run.json` stores `result_fingerprint`: the SHA256 of the text formed by
    one line `<sha256>  <relative path>\n` per result-content file, sorted by path. `summary.json`
    doesn't contain the fingerprint, which would be circular.
  - **Creating the golden (owner only).**
    - `gval reference persistence --split-id <id> --tier quick --split validation`, through
      `scripts/reference_delta.sbatch` on a **CPU** node (`--device cpu`, 1 thread:
      `OMP_NUM_THREADS=1`, `torch.set_num_threads(1)`). It runs exactly the normal evaluation code path
      with the persistence adapter.
    - It writes `references/<split_id>/forecast_v1/persistence_quick/<platform>/`, containing:
      - the result-content files;
      - `run.json`;
      - `golden.json`: `{result_fingerprint, files: {path: sha256}, platform, environment_locked,
        lock_sha256, repo_commit, provisional}`.
    - `provisional` is `true` while the platform has no environment lock. Once a lock is committed,
      the owner regenerates the golden with `provisional: false`.
    - The command refuses to overwrite an existing golden with different content. A changed golden
      requires a new protocol version or a recorded owner decision.
  - **Conformance (everyone).**
    - `gval conformance --split-id <id>` runs the same persistence quick-tier validation evaluation on
      CPU with 1 thread. Output goes to `staging/<user>/conformance/<platform>__<n>/`, **never** to
      `runs/`, so it never appears on the leaderboard.
    - It then compares its `result_fingerprint` with `golden.json` for the **same platform**. Pass =
      identical fingerprint. On failure it reports which files differ, and for JSON numbers the largest
      relative difference.
    - If only the other platform has a golden, conformance compares every number within 1e-12
      relative and reports `status: warn` with `cross_platform: true`. That is not a failure, but it
      is recorded.
    - If no golden exists, it fails with `next: "ask the owner to run scripts/reference_delta.sbatch"`.
    - Every agent runs conformance once per environment (platform + lock) before its first
      submission. `run.json` of later runs records the last passing conformance fingerprint.
  - **Learned models on GPU.** Two runs of the same request must have result-content numbers that
    agree within `gpu_tolerance` = 1e-4 relative. `gval verify --compare <run_a> <run_b>` checks this.
  - **Milestone 2 bootstrapping.** No golden exists yet. The implementer delivers the commands and the
    Slurm script, and tests them against a synthetic split in a temporary directory. The owner then
    runs `scripts/reference_delta.sbatch` for `rc300_reduced_v1` and `5000run_v1` (provisional, on
    DeltaAI). After that, `gval conformance` on real data is part of the milestone 2 review.
