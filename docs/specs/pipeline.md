# Spec: end-to-end validation pipeline (v1)

Status: approved for implementation (2026-11-14); all protocol settings are decided. The owner of the repository and of this spec is the benchmark owner;
the planner maintains this text. The implementer follows it exactly.

- Every protocol setting lives in `protocols/forecast_v1.json`, so changing one never needs a code
  change.
- Anything not covered here is a question for the planner, not a decision for the implementer.

## 0. Goal and principles

Group members train different GRMHD forecasting models (TRON, ViT, UNO variants, …) on shared data.
This repository is the single way to validate them, so that every result is comparable and anyone can
pick up anyone else's results.

1. **One contract.** Every model is evaluated on the same data (frozen split files), with the same start
   points and horizons (a frozen protocol file), the same metric code and the same output layout.
2. **Agents run the pipeline; they don't write it.** A user, or their agent (Claude Code, Codex, or any
   other), writes exactly two things: an adapter for their model and a run request. Everything else
   (which dumps, which metrics, every path and filename) is decided by the code.
3. **Same inputs → same outputs.** The same model, checkpoint and protocol must produce the same files
   with the same names. Numbers must be bit-identical on CPU and within a stated tolerance on GPU.
4. **Physical units.** Data, adapter inputs and adapter outputs are physical (unnormalized). Only the
   "loss-space" metrics (section 4) use the fixed TRON normalization. Everything else is physical.
5. **Shared and recorded.** Results live in one group folder on Delta/DeltaAI. Every evaluation,
   including repeated test runs and failed runs, is recorded.

## 1. Names

- Repository: `grmhd-emulator-validation` (public GitHub, owner YongseokJo).
- Python package: `grmhd_validation`. CLI: `gval`.
- Shared folder: `/work/nvme/bgun/share/validation` (group `delta_bgun`; Delta and DeltaAI share /work).
- `split_id`: e.g. `rc300_reduced_v1`, from the split file. `protocol_id`: e.g. `forecast_v1`.

## 2. Data contract (done; frozen)

- `splits/<split_id>.json` (schema_version 2), generated by `splits/make_splits.py`. Never edit one; a
  change is a new version. The structure:
  - `segments`: the whole run in time order.
  - `splits.{train,validation,test,excluded}`: each with `chunks` and per-dump `files`, relative to
    `data_root`.
- v1 layout: three validation and three test chunks at separate positions, with 10 excluded dumps on
  each side of every chunk. See `split_rule` in the file.
- The code reads dumps **only** through the split file. It never lists data directories. Paths are
  `data_root` + file. A `--data-root` override is allowed (for other machines), but the split file's
  identity is its SHA256 and doesn't depend on the path.
- **Per-file checksums.** Owner-run Slurm job `gval checksums --split-file …` writes
  `checksums/<split_id>.sha256` (sha256sum format, path relative to `data_root`). Evaluation verifies
  the SHA256 of every dump it reads against that file. It fails if a hash is missing or wrong, unless
  `--no-verify-data`, which is recorded in `run.json` and marks the run unverified.
- Known data issue (recorded in the split files): rc300 cells with r < 6.11 are a coarse AMR level, each
  value duplicated into 2 × 2 × 2 cells. 5000run uses only the main-folder dumps; `blind/` is outdated.

## 3. Evaluation protocol

`protocols/forecast_v1.json` holds every setting below. The runner reads it; nothing in it is a CLI flag.

### 3.1 What a model is given and scored on

- **Eligible windows.** Evaluate only on validation or test chunks. Every history frame, start frame and
  target frame of a sample lies inside **one** chunk.
- **History.** At start dump s, the adapter receives the true frames `s − h + 1 … s`, where h is the
  adapter's `history_length` (1 ≤ h ≤ `H_max`). It receives nothing later than s.
- **Same starts for every model.** In each chunk, eligible starts are
  `[chunk_first + H_max − 1, chunk_last − max_steps]`, whatever h a model uses.
  - `H_max` = 10.
  - Single-step metrics use every eligible start.
  - Rollout analyses use `n_starts_per_chunk` starts, evenly spaced over the eligible range:
    `round(linspace(lo, hi, n))`, de-duplicated.
- **Rollout.** Autoregressive. After step 1, the adapter's own outputs become its history, mixed with
  the true frames still inside the window, i.e. the standard rolling buffer. The runner, not the
  adapter, keeps that buffer.
- **Horizon.** `max_steps` = 50 steps, scored at `report_steps` = 1, 10, 25 and 50 (Kevin's
  defaults).

### 3.2 Analyses (all from Kevin's suite, `Fall26/eval/evaluate_forecast_ds.py`)

The protocol lists which analyses run in each tier; v1 runs all of them.
Tiers:
- `quick`: single_step, rollout_curve. Minutes; used during development.
- `full`: every analysis listed in the protocol. Required for the leaderboard.

| Group | Analyses (Kevin's `--mode` names) |
|---|---|
| ML core | single_step, rollout_curve (with predictability horizon and attractor saturation), error_correlation, correlation_times, stability, cost |
| Physics | physics_table, shell_profiles, temporal_consistency (conservation drift), conservation_closure, accretion_diagnostics (Φ, P_jet, η, φ_BH, Ṁ correlation), mdot, lorentz, mean_profiles |
| Statistics and structure | statistical_props (JS divergence), spectrum, azimuthal_spectra, coherence, temporal_spectrum, turbulence_stats (structure functions), conditional_error, bias_analysis, spatial_error |
| Figures | meridional_slice, rollout_evolution |

`error_spectra` is deprecated in Kevin's code; drop it.

## 4. Metric spaces

- **Loss space.** The fixed TRON normalization, identical to `Fall26/common/normalizer.py`: log10 for
  rho and ug, arcsinh for utilde and B. It is applied by the benchmark to the physical truth and the
  physical prediction, whatever normalization the model trains with. Used only for: nMAE, skill vs
  persistence (single-step and rollout curve), predictability horizon, and attractor saturation.
- **Physical space for everything else.** Error maps, conditional error, bias analysis, error
  correlation, stability (perturbation and output measured in physical units, relative to each
  channel's training-split RMS), distributions, spectra and every physics quantity.
  - For each analysis, the implementer writes `docs/metrics.md`. It gives the formula, the space, the
    units, the averaging, and how it differs from Kevin's original.
  - If moving an analysis from normalized to physical space changes its meaning, flag it for review.
- Physical relative errors need a reference scale. Use the training-split per-channel mean of |x| or
  RMS, computed once by the owner into `references/<split_id>/channel_scales.json` from training dumps
  only. Every run uses this file.

## 5. Required improvements over Kevin's suite (all approved)

1. **Port, don't wrap.** Turn the 3,500-line script into modules under `grmhd_validation/analyses/`,
   one per analysis. Each has the signature `run(ctx) -> dict` and writes JSON (plus CSV for tables)
   with a fixed schema. No text output is parsed, ever. `out_res.txt` is still written, but only as a
   human-readable rendering of the JSON.
2. **Regression against the original.** Where a method is unchanged, the port must reproduce Kevin's
   numbers. Golden test: persistence, plus one fixed TRON checkpoint, on a fixed dump range, run
   through both the original script and the port; they agree within 1e-6 relative.
   - Every intended change (items 3–9) gets its own test and an entry in `docs/metrics.md`.
3. **Statistics over all starts.** Physics tables, drift, Lorentz, spectra and slices are averaged over
   all rollout starts, with 95% CIs, instead of following one rollout from one start.
4. **Bootstrap.** A block bootstrap over starts that respects chunks: resample whole blocks of
   `bootstrap_block` consecutive starts within a chunk. Seed and number of resamples come from the
   protocol. This replaces Kevin's "every second pair".
5. **Correct accretion physics.** Compute Ṁ, Ė, L̇, P_jet and η from the full 4-velocity: u^t from the
   normalization u·u = −1 with the metric, then u^r. Never use `utilde1` as u^r.
6. **rc300's coarse ring.** Horizon quantities (Φ(r_H), P_jet, φ_BH, Ṁ(r_H)) are computed in the coarse
   AMR ring.
   - Report them flagged `coarse_ring: true`.
   - Also report the same quantities at the first resolved shell, r ≥ 6.11.
   - The leaderboard headline uses the resolved shell.
7. **Dataset- and model-agnostic.** No hard-coded paths, Δt, spins or "TRON" strings. Time-based
   results are reported in steps, in R_g/c, and in units of τ_c.
8. **Fixed outputs.** Figures have fixed names (`figNN_<analysis>.png`), sizes, DPI and fonts, and no
   timestamps in their metadata.
9. **Truth-only quantities cached per split.** Correlation times, truth spectra, truth shell profiles
   and persistence baselines are computed once by the owner into `references/<split_id>/<protocol_id>/`,
   then reused. Every model is then compared against identical truth statistics.

## 6. Plugging in a model (adapter contract)

A user keeps their model code in their own repository. They add one adapter file and never touch this
repository's code.

```python
from grmhd_validation import ModelAdapter, Geometry

class Adapter(ModelAdapter):
    name = "tron"              # [a-z0-9-]+, unique on the leaderboard
    version = "v1"             # bump when architecture/training changes
    history_length = 1         # frames needed, 1..H_max
    max_batch = 1              # starts the runner may batch together

    def __init__(self, checkpoint: str, geometry: Geometry, device: str, options: dict):
        ...                    # load weights; restore the model's own normalization from the checkpoint

    def step(self, history):   # torch.float32 [B, h, 8, Nr, Nθ, Nφ], physical, on `device`
        ...                    # return torch.float32 [B, 8, Nr, Nθ, Nφ], physical

    # optional: override if the model predicts several steps at once
    def rollout(self, history, n_steps):   # -> [B, n_steps, 8, Nr, Nθ, Nφ]
        ...
```

- `Geometry` provides r, θ, φ, the metric, gdet, dx, spin, dt_dump and `resolved` as tensors. It
  contains no data paths: adapters get data **only** as arguments.
- The adapter does any normalization, clamping, floors or Lorentz limits itself. **The output is scored
  as returned**; any non-finite value or wrong shape or dtype fails the run.
- The adapter is referenced as `/abs/path/adapter.py:Adapter`, or as an installed entry point in group
  `grmhd_validation.adapters`.
- Its source SHA256, and the git commit of its repository if there is one, go into `run.json`.
- Ship `adapters/persistence/` (h = 1, returns the last frame) and `adapters/tron_example/`, ported from
  `Fall26/eval/evaluate_tron.py` on branch `fall26-tron-rc300`, as references.
- Helper commands:
  - `gval new-adapter <dir>` writes a template adapter plus `run_request.json`.
  - `gval check-adapter <ref> --checkpoint …` runs on a few validation dumps. It checks shapes, dtype,
    finiteness, that two calls give identical output in eval mode, that `history_length` is honoured,
    and memory and time per step. It prints a JSON verdict.
- **Run request** (`run_request.json`, the only other user-written file):
  `{model: name, version, adapter: ref, checkpoint: path, options: {}, training_record: path|null, notes: ""}`.
- Docs: `docs/plugging_in_a_model.md`, a step-by-step walkthrough with the TRON example.

## 7. Running and outputs

- Commands:
  - `gval evaluate --request run_request.json --split-id <id> --split validation|test --tier quick|full`.
  - Slurm wrappers: `scripts/evaluate_delta.sbatch` (A100) and `scripts/evaluate_deltaai.sbatch`
    (GH200).
- **run_id** is decided by the code: `<model>-<version>__<ckpt_sha8>__<split>__<tier>__a<N>`. N is the
  attempt number: 1 + the number of existing directories with the same prefix, in `runs/` and in
  `staging/`, complete or not.
- Every attempt keeps its directory, so repeated test runs are visible (test discipline = **record**).
- Layout of one run (exact names):

```
runs/<split_id>/<model>/<run_id>/
  run.json          request, attempt, user, host, GPU, CUDA/torch/numpy versions, env lock SHA256,
                    this repo's commit, adapter SHA256 + repo commit, checkpoint SHA256,
                    split file SHA256, protocol SHA256, data verified (bool), start/end time
  summary.json      headline numbers for the leaderboard (fixed schema)
  metrics/<analysis>.json         one per analysis
  tables/<analysis>.csv           where an analysis has a table
  figures/figNN_<analysis>.png    fixed list per protocol
  out_res.txt       human-readable rendering of metrics/
  logs/evaluate.log
  checksums.json    SHA256 of every file above
  COMPLETE          written last, only if everything succeeded
```

- The runner writes into `staging/<user>/<run_id>/`. On success it writes `COMPLETE`, makes the tree
  read-only (`chmod -R a-w`), then moves it into `runs/<split_id>/<model>/` with `rename`, which is
  atomic on the same filesystem. On failure the directory stays in staging with `FAILED` and the
  traceback. It still counts as an attempt.
- `gval verify <run_dir>` re-checks the checksums, the schemas and the split/protocol hashes.

## 8. Shared folder and permissions (created; owner gkerex, group delta_bgun)

```
/work/nvme/bgun/share/validation/          2750, group read-only
  splits/            frozen split files (444); owner writes
  checksums/         per-file SHA256 lists; owner writes
  references/        channel scales, truth statistics, persistence golden; owner writes
  reports/           leaderboard and comparison figures; owner writes (single writer)
  movies/            data movies; owner writes
  runs/              3770 + sticky: everyone creates, nobody deletes others' entries
  staging/           3770 + sticky: per-user work area, runs/ is only reached by rename
  training_records/  3770 + sticky: provenance of checkpoints (section 9)
```

- Owner-only directories have ACLs `g::r-x` plus the same as default.
- Group-writable directories inherit default ACLs `g::rwx`, so files are group-readable whatever a
  user's umask is.
- The CLI must, every time:
  - set `os.umask(0o007)` at start;
  - create `runs/<split_id>/<model>/` and `staging/<user>/` with mode 3770 (setgid + sticky);
  - make completed runs read-only;
  - never `chmod` anything it didn't create.
- **Agents never copy files in by hand** (`cp`/`rsync` from a home directory keeps 600 permissions);
  only `gval` writes here. `gval doctor` checks write access and the group, and reports any file in the
  tree that the group can't read.

## 9. Training provenance (record, not required)

- `gval record-training --request run_request.json --split-id <id> --config <training config> [--log …]`
  writes `training_records/<model>/<ckpt_sha8>.json`.
- It records: split file SHA256, the chunks used for training and for checkpoint selection, where the
  normalization statistics were fitted (must be train), the training code commit and the config.
- `run.json` links it. The leaderboard shows "trained on this split: yes / no / unknown".

## 10. Reporting and the leaderboard

- `gval report --split-id <id>` (owner only):
  - reads every `COMPLETE` run;
  - verifies it;
  - writes `reports/<split_id>/leaderboard.{json,csv,md}` and comparison figures (rollout curves of all
    models, skill bars).
- One row per run. Columns:
  - headline skill and nMAE (loss space);
  - physical relative errors per channel;
  - key physics errors;
  - number of test attempts for that model and checkpoint;
  - data verified;
  - training provenance.

  Rows are sorted by model, then run_id. Numbers have fixed formatting.
- Only compare rows with the same `split_id`, `protocol_id` and tier. The report states this rule.
- **GitHub.**
  - The owner commits `reports/<split_id>/leaderboard.md`, the comparison figures and each run's
    `summary.json` + `run.json` (under `results/<split_id>/<model>/<run_id>/`) through a PR.
  - CI checks the schemas and that `leaderboard.md` is exactly what `gval report --from-results`
    regenerates from the committed results. Nobody edits it by hand.
  - Full bundles stay on Delta.

## 11. Reproducibility

- **Environment.** Locks are *recorded* from real environments, never written by hand. There is one lock
  per platform, because Delta (x86_64, A100) and DeltaAI (aarch64, GH200) cannot share binaries.
  - `environment/requirements.in`: direct dependencies with lower bounds only (numpy, scipy, matplotlib,
    torch, jsonschema, plus whatever the ported analyses import). The implementer writes it in
    milestone 1.
  - `environment/platforms.json`: per platform, how the base environment is loaded.
    - `delta-x86_64`: `module reset; module load pytorch-conda/2.8`. Not 2.12, whose matplotlib can't
      save PNGs (see Kevin's `Fall26/scripts/env_delta.sh`).
    - `deltaai-aarch64`: there is no pytorch-conda module on DeltaAI. Leave it `null` until the owner
      names the base environment.
  - `scripts/record_lock.sbatch <platform>`: run by the owner on a compute node of that machine. It
    loads the base environment, installs this package, and writes `environment/<platform>.lock`. The
    lock holds the Python version, torch version + CUDA version, and `pip freeze --all` sorted. The
    owner commits it.
  - `gval doctor`:
    - **no lock for the current platform:** status `warn` with `"environment_locked": false`. Doctor
      still succeeds, so milestones 1–2 can proceed.
    - **lock present:** a mismatch in python, torch, CUDA, numpy, scipy or matplotlib is a **fail**;
      any other package mismatch is a `warn`.
  - `run.json` records the platform, the lock SHA256 (or null) and `environment_locked`. The leaderboard
    shows runs from unlocked environments as "unlocked"; the owner's dry run (milestone 7) requires a
    lock.
- **Determinism.** Fixed seeds from the protocol, `torch.use_deterministic_algorithms(True)` where
  supported, eval mode, no autocast unless the adapter enables it (recorded).
- **Golden conformance.**
  - The owner publishes `references/<split_id>/forecast_v1/persistence_quick/` (and the full tier).
  - `gval conformance` runs persistence on CPU and must match it **bit for bit** (float64 accumulation,
    fixed reduction order).
  - Every agent runs this once per environment before its first submission.
  - For learned models on GPU, two runs must agree within `gpu_tolerance` = 1e-4 relative on
    summary.json numbers.

## 12. Agent instructions (deliverables)

- `AGENTS.md`: the canonical, tool-agnostic instructions, read by Codex and any agent. In this order:
  1. what this repo is;
  2. the only files a user writes;
  3. the exact command sequence: `doctor → conformance → new-adapter → check-adapter → evaluate
     --tier quick --split validation → evaluate --tier full --split validation → evaluate --tier full
     --split test`;
  4. what to report back;
  5. forbidden actions: editing `splits/`, `protocols/`, `grmhd_validation/` or `references/`;
     copying files into the shared folder; re-running test to improve a number; reading dumps outside
     the history the runner passes.
- `CLAUDE.md`: imports `@AGENTS.md`, plus Claude-only notes.
- `.claude/skills/validate-model/SKILL.md`: the same sequence as one skill.
- `.claude/settings.json`: denies Edit/Write on the protected paths.
- `docs/agents/generic.md`: the same as AGENTS.md, for agents with neither convention. It's
  generated from AGENTS.md, and CI checks they match.
- Every command prints one JSON object on its last line: `{"ok": bool, "next": "<the next command>", …}`.
  Agents follow `next`. Errors say what to do.

## 13. Tests and CI

- Unit tests per analysis on synthetic geometry.
- Golden regression against Kevin's original (section 5.2).
- Conformance (11).
- Permissions behaviour, using a temporary directory with the same modes.
- Schema validation of every output.
- Determinism (run twice, compare `checksums.json`, figures excluded).
- CI on GitHub runs everything that needs no Delta data. Data-dependent tests are a Slurm job: owner
  runs `scripts/ci_delta.sbatch` before merging.
